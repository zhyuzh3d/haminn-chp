CHP 是一套**本机模型能力接口规范**，面向“把画布交给后端重画”“把一句话交给本机引擎念出来”这一类客户端。它规定的是**输入输出格式**，不规定后端用什么模型、什么节点、什么采样器。

参考实现是 `haminn-chp` 仓的 `hamdraw_chp` 包（ComfyUI 自定义节点，也支持 `python -m hamdraw_chp serve` 独立运行）；插件本身也叫「**CHP 插件**」，简称 **CHPCP**。**协议名与实现名是两件事**：`CHP` 是这套规范，`hamdraw_chp` 是它的一个实现，将来可以不止一个。

## 0. 三条设计原则

1. **规范只定对外契约。** 字段名、字段含义、取值范围、错误码属于规范；用什么模型、怎么搭图、怎么加速属于实现。同一个字段在不同实现里可以用不同机制达成，只要**方向与值域一致**。
2. **路径不版本化。** 协议版本号放在响应体里，路径永久不变。客户端永远不需要“猜新版路径”。
3. **同一个 `spec` 内只加不删；跨大版本不承诺兼容。** 大版本内：服务端只新增字段、新增场景；不删字段、不改已有字段的含义、不改已发布场景的 `category`。客户端**必须忽略**不认识的字段与不认识的场景。**跨大版本则是另一回事**：`spec` 变了就意味着这份契约不再承诺读得动上一版，客户端**见到不认识的 `spec` 应当自报“插件版本比应用新”并停下**，而不是照着旧规则继续猜 —— 猜出来的请求体在新版里可能只是被忽略，那会比报错更难查。

## 1. 四类接口

| 类别 | 路径 | 鉴权 | 用途 |
|---|---|---|---|
| **信息** | 由 `endpoints.info` 给出（推荐 `/chp/info`） | **需要 key**（且只在配了 key 之后才强制；§1.1.1） | 客户端开机第一件事：**我这把 key** 能用什么 |
| **生成** | 由 `endpoints.jobs` 等给出 | 见 §4.7 | 提交作业、取结果、取消 |
| **进度** | 由 `endpoints.progress` 给出 | 见 §4.7 | 高频轮询的轻量接口 |
| **语音** | 由 `endpoints.speech` 给出（推荐 `/chp/speech`） | 见 §4.7 | 一次请求、边合成边回字节，**不套作业模型**（§4.8） |

分四类的目的：客户端**先拿到自己那把 key 能用的清单再干活**；高频轮询不碰结果解析；语音那条路不欠作业模型那一整套（排队位次、进度、取消、分件取回对一句话全是死重）。

**信息接口曾经是公开的**，本版改成需要 key，理由只有一条：**文档内容从此依赖 key**（不同 key 看到的能力不同）⇒ 未授权状态下已经没有「正确的文档」可答。原设计想告出的那两件事（地址对不对、密码对不对）一件没丢，只是分得更清：

| 现象 | 含义 |
|---|---|
| 连不上 / 超时 | 地址不对，或服务没起 |
| **`401`**（响应体带 `spec`，见 §1.1.1） | **地址对、是 CHP、但 key 不对** |
| `200` 但 `spec` 不是 `chp/*` | 地址通了，但那不是 CHP |

### 1.1 信息接口

**需要 key**（前提见 §1.1.1）。它的地址**就是用户填进客户端的那个地址**（见 §1.3），这一点没变。

```json
{
  "spec": "chp/2",
  "plugin": { "id": "hamdraw_chp", "version": "3.2.0",
              "label": { "zh": "CHP 插件（CHPCP）",
                         "en": "CHP plugin (CHPCP)" } },
  "auth": { "required": true, "authorized": true, "scheme": "Bearer",
            "header": "Authorization", "hint": "密码在 ComfyUI 的 CHP 插件配置节点里设置。" },
  "endpoints": {
    "info":     "/chp/info",
    "jobs":     "/chp/jobs",
    "job":      "/chp/jobs/{job_id}",
    "progress": "/chp/jobs/{job_id}/progress",
    "output":   "/chp/jobs/{job_id}/output/{index}",
    "cancel":   "/chp/jobs/{job_id}/cancel",
    "translate":"/chp/translate",
    "speech":   "/chp/speech"
  },
  "rules": [ { "…": "见 §3" } ],
  "abilities": [ { "…": "见 §4.2" } ],
  "input_schemas": { "txt-ref-2-img/v1": { "…": "见 §4.1" },
                     "txt-msk-ref-2-img/v1": { "…": "见 §4.1" } },
  "translation": { "…": "见 §5" },
  "speech": { "…": "见 §4.8" }
}
```

**顶层键就是这九个**：`spec` / `plugin` / `auth` / `endpoints` / `rules` / `abilities` / `input_schemas` / `translation` / `speech`。规范之后可能新增顶层键，客户端**必须忽略**不认识的；实现也可以多播报**自己的**键（参考实现就多一个 `errors`，列出它认得的错误码，客户端据此把回执翻成人话）。

- `spec` 是**协议版本**，是整份文档里唯一表示“你是哪一版规范”的字段。
- **任何一层都允许多余字段**（`rules` 条目、`abilities` 条目、`frame` 条目）。CHP 播报但**不解释**它们，写这个字段的客户端自己读 —— 这是“谁都能给自家客户端加字段而不必改插件源码”的骨架，不是客套。要加一个**新场景**才需要改实现。

#### 1.1.1 信息接口的授权，与两个边界

**播报按 key 过滤。** `rules` / `abilities` / `input_schemas` / `speech` 全部**只播报这把 key 授权到的那部分**。理由与 §4.2「文档不能声称一个它不会用的模型」是同一条：客户端的能力槽是按 `signature` 匹配的，文档里若有一条它打不通的规则，界面上就会出现一个点不动的选项。

> **播报过滤不是权限。** 知道 `category` 名字的人可以绕过界面直接 `POST`。**「看不到」是障眼法，「拒收」才是权限** ⇒ 执行层必须再校验一次（§4.7）。

**`auth` 段保留**（删字段是破坏）：`required: true`、`authorized: true` —— 语义是「本服务需要钥匙，而你带的这一把是对的」。未授权时**不返回文档**，返回下面那个 `401`。

**`401` 的响应体要能自证是 CHP**（在 §6 的既有形状上**只多一个 `spec`**）：

```json
{ "error": "unauthorized", "spec": "chp/2", "message": "访问密码不正确…" }
```

客户端据此**不必靠猜 URL** 就能把「是 CHP、只是钥匙不对」与「那里根本没有插件」分开 —— 这两种情况给用户的下一步动作完全不同。**只有 401 带 `spec`**，其余错误码的响应形状一个字节都没变（客户端是按形状解析的）。

**一把 key 都没配时，服务是公开的** —— 与上一版**逐字相同**，老用户零改动：

| 部署形态 | 行为 |
|---|---|
| **没配任何 key**（key 表为空，且配置里的密码与环境变量都为空） | `/chp/info` ⇒ **200、能力全在**，`auth.required: false` |
| **配了至少一把 key** | `auth.required: true`；无 key / 错 key ⇒ **401**；每个端点都校验 |

⇒ 「不设全局『对外可用』开关」（§4.7）的准确表述是：**那个开关就是「有没有配 key」这一件事**，不需要第三个布尔量。

### 1.2 生成接口

| 方法 | 用途 |
|---|---|
| `POST` `endpoints.jobs` | 提交 → `202` `{"job": {…}}` |
| `GET` `endpoints.job` | 状态 + 结果（较重，完成后再调） |
| `GET` `endpoints.output` | 取图，`image/png` 直出 |
| `POST` `endpoints.cancel` | 取消排队中的作业 |

提交体的字段定义见 §4。`202` 返回完整 `job` 对象（结构见 §1.4）。

### 1.3 `endpoints`：地址从文档里读

| | 内容 |
|---|---|
| **规则** | 信息接口**需要 key**（边界见 §1.1.1）；它的地址**就是用户填进客户端的那个地址**；其余接口的地址**一律从信息文档的 `endpoints` 里读**，客户端**不许自己拼路径** |
| **推荐** | 信息接口在 `/chp/info`，其余在 `/chp/` 下（**八个键**，见 §1.1） |
| **端口** | **不规定**。挂在哪个端口是后端自己的事，不是协议的事 |
| **取值** | `endpoints` 的值以 `/` 开头 = 相对信息接口的**同源路径**；否则按**绝对 URL** 处理 —— 一个实现想把任务接口放到别的机器上，不必改协议 |
| **占位符** | 路径里的 `{job_id}` / `{index}` 由客户端替换 |

**客户端解析写死成一条**（不是猜）：把用户填的地址**原样**当信息接口请求；若它不是 CHP 文档、且地址里没有路径，**再试一次推荐的 `/chp/info`**；两次都不成 ⇒ 报「这个地址不是 CHP 服务」。这一条同时兼容用户存下来的三种写法：裸源、`…/chp`、`…/chp/info`。

⚠ **`401` 必须当场停下，不许当成「这个候选地址不对」继续试下一个**（§1.1.1 那个带 `spec` 的响应体就是为这件事准备的）。照旧逻辑把它咽掉，用户拿错钥匙时会看到「这个地址不是 CHP 服务，请确认插件已安装」——把他指向完全错误的排查方向。

### 1.4 `job` 对象

```json
{
  "id": "8f3c…",
  "category": "fast",
  "state": "queued | running | completed | failed | cancelled",
  "queue_position": 2,
  "progress": null,
  "created": 1758783600.12,
  "typical_seconds": 1.2,
  "resolution": "512x512",
  "seed": 12345,
  "ref_strength": 0.55,
  "ext_params": { "step": 8 },
  "prompt": "a cat on a sofa",
  "prompt_source": "一只猫在沙发上",
  "translated": true,
  "ignored": ["negative_prompt"],
  "outputs": [
    { "index": 0, "url": "/chp/jobs/8f3c…/output/0",
      "media_type": "image/png", "filename": "hamdraw_00001_.png",
      "subfolder": "hamdraw/fast", "type": "output" }
  ],
  "error": "节点名: 原因"
}
```

- `resolution` / `ref_strength` 是**生效值**，回填给客户端：一个被夹过边界的权重、一个因为省略而取了默认的画幅，客户端必须读得出来自己实际拿到的是什么，而不是以为它发的那个数生效了。
- `ext_params` 是**原样带回**的那个对象（见 §4.4），所以客户端放进去的自家字段能读回去。
- `typical_seconds` 只是**参考值**（参考实现的实测量级），客户端不得据此推算进度。
- `prompt` 是**实际送进模型的那份**（可能是自动翻译的结果），`prompt_source` 是客户端给的原文，`translated` 表示两者是否不同。客户端把 `prompt_source` 显示给用户，把 `prompt` 用于复现。
- `ignored` 列出本次请求里**被忽略的顶层字段**。客户端据此提示用户，而不是让用户以为自己设的参数生效了。**这条回执不是可选项** —— 没有它，参数改名对客户端就是静默失效。
- `outputs[].url` 是绝对路径，客户端**不要**再拼一次 base。
- `progress` 允许为 `null`，而且经常就是 `null`（见 §1.5）。

### 1.5 进度接口

高频轮询用，只返回四个字段，不做结果解析：

```json
{ "job": { "id": "…", "state": "running", "queue_position": 0, "progress": null } }
```

**`progress` 允许为 `null`，而且经常就是 `null`。** 规范不要求后端能给出百分比 —— 编一个假的百分比比给 `null` 更糟。`null` 时客户端应显示“进行中”这类不确定态。

`queue_position` 是前面还有几个作业（自己在跑时为 `0`，未知为 `null`）。这个数任何实现都算得出来，是可靠的。

## 2. IO 规则 `rules`

规则声明“吃什么、吐什么”。**规则名就是签名**：机器读的字符串，客户端据此判断“我能不能处理这个场景的输出”。

```
<规则> ::= <输入模态>("-" <输入模态>)* "-2-" <输出模态>
<模态> ::= txt | ref | msk | img | glb | 3dgs | sph
规范序 ::= txt [msk] ref
```

规则（必须遵守，否则规则名不可比较）：

- **按字面 `-2-` 切分**，左侧是输入模态、右侧是输出模态。因为分隔符是三个字符，`txt-ref-2-3dgs` 里的 `3` 不再有歧义 —— `chp/1` 那条“签名里除分隔符 `2` 以外不出现数字”的禁令随之取消。
- **模态只写对象类型，不写参数名。** `txt` 是文本提示词、`ref` 是参考图、`msk` 是蒙版、`img` 是位图、`glb` 是 glTF、`3dgs` 是高斯点云、`sph` 是语音（§4.8）。
- **必须按规范序写。** `msk-ref-txt-2-img` 不是“另一种写法”，而是**非法** —— 规则名要能被客户端当字符串相等比较，所以只能有一种拼法。
- `ref` = 恰好一张参考图。

图像侧目前只有两条规则（语音侧那条 `txt-2-sph` 与它自己的两张表一起放在 §4.8）：

| 规则 | 输入 | 输出 | 用它的场景 |
|---|---|---|---|
| `txt-ref-2-img` | 文本 + 一张参考图 | 图像 | `fast` / `upscale` / `render` |
| `txt-msk-ref-2-img` | 文本 + 蒙版 + 一张参考图 | 图像 | `inpaint` |

**规则必须支持的参数**（收敛清单，模型缺哪个就在中间工作流里模拟出来）：

| 规则 | 必须支持 |
|---|---|
| `txt-ref-2-img` | `prompt`、`resolution`、`seed`、**`ref_strength`**（方向 0.05–0.95，越大越贴近参考图） |
| `txt-msk-ref-2-img` | 同上 + `mask_base64`（白 = 要重画） |

`ref_strength` 就是“模拟”的现成范例：一个家族把它换算成去噪强度，另一个家族没有可保留的初始 latent，就改成柔化参考图。**方向与值域一致、机制各自决定，这正是规范与实现的分界线**（见 §4.6）。

## 3. 场景 `rules[]`

场景是**客户端要什么**；`abilities[]`（§4.2）是**什么能回答**。一条 `rules` 条目：

```json
{
  "category": "fast",
  "rule": "txt-ref-2-img",
  "signature": "txt-ref-2-img",
  "input": "txt-ref-2-img/v1",
  "label": { "zh": "快速生图", "en": "Quick draw" },
  "description": { "zh": "…", "en": "…" },
  "prompt": { "language": "en" },
  "needs": { "prompt": true, "image": true, "mask": false },
  "defaults": { "ref_strength": 0.55 },
  "typical_seconds": 1.2
}
```

| 字段 | 规范键? | 含义 |
|---|---|---|
| `category` | **是** | 场景名。这是客户端**唯一要认**的词，同时是**请求体字段名**（§4.3）。 |
| `rule` | **是** | 引用 §2 的规则表。改规则拼法只改这一处。 |
| `signature` | 否 | 由 `rule` 在文档生成时算出，等于规则名。给“只想比较签名”的客户端一条直路，**不需要客户端自己解析 `rule`**。 |
| `input` | 否 | 由 `rule` 算出，指向 `input_schemas` 的键。同一规则共用一份 schema。 |
| `label` / `description` | 否 | 双语显示名与说明。客户端读不到就用自己的文案。 |
| `prompt.language` | 否 | `"en"` = 文本编码器只吃英文（触发 §5 的自动翻译）；`"any"` = 能读中文。 |
| `needs` | 否 | 哪些输入是必需的，决定 §4.3 里哪些字段必填。**规则说的是“能吃什么”，`needs` 说的是“必须给什么”**，二者都对：`render` 的规则是 `txt-ref-2-img`（带参考图就是参考图编辑），而 `needs.image = false`（不带就是纯文生图）。 |
| `defaults` | 否 | 客户端不传时的取值。 |
| `typical_seconds` | 否 | 参考耗时，非承诺。 |

**除 `category` 与 `rule` 之外都是参考实现定义的可选键**，客户端读到就用、读不到就用自己的那份。

### 3.1 场景是开放集合，但**没有别名**

客户端必须忽略不认识的 `category`。**一个场景只有一个名字**：`chp/2` 起不保留历史名或旧客户端用名 —— 客户端漏改时会在 `job.ignored` 里看到自己发错的那个字段名（§4.3），而不是被静默地服务了另一个场景。

### 3.2 当前场景（参考实现）

| `category` | `rule` | `prompt.language` | 画幅（`frames` 首项即默认） | 参考图权重默认 |
|---|---|---|---|---|
| `fast` | `txt-ref-2-img` | `en` | 1:1 `512x512`；4:3 `576x384`；3:4 `384x576` | 0.55 |
| `inpaint` | `txt-msk-ref-2-img` | `en` | 同 `fast`（蒙版必须与画布同尺寸） | 0.30 |
| `upscale` | `txt-ref-2-img` | `en` | 1:1 `1024x1024`、`2048x2048` | 0.75 |
| `render` | `txt-ref-2-img` | `any` | 1:1 `1024x1024`、9:16 `768x1344`、16:9 `1344x768`、3:4 `832x1152`、4:3 `1152x832`、2:3 `832x1216`、3:2 `1216x832`、21:9 `1536x640` | 0.95 |

步数**不在规范里**：它是参考实现自己的扩展键 `ext_params.step`（§4.4）。

## 4. 请求体

### 4.1 共享输入 schema

同一规则的场景**共用一份 schema**，所以客户端写一次调用逻辑就能调所有 `txt-ref-2-img` 场景。`input_schemas` 里目前恰好两份：

- `txt-ref-2-img/v1` —— 基础那份。
- `txt-msk-ref-2-img/v1` —— **由基础那份加一个必填的 `mask_base64` 生成**，不是抄一遍。这是规范对实现的硬要求：手抄两份，改一处漏一处的日子迟早会来。

### 4.2 能力 `abilities[]`

**一条 `abilities` 条目 = 一组能跑起来的模型文件**，不是单个文件：

```json
{
  "name": "DreamShaper8_LCM.safetensors",
  "files": { "checkpoint": "DreamShaper8_LCM.safetensors" },
  "ready": true,
  "missing": [],
  "frames": [
    { "ratio": "1:1", "category": "fast",    "resolution": ["512x512"] },
    { "ratio": "4:3", "category": "fast",    "resolution": ["576x384"] },
    { "ratio": "3:4", "category": "fast",    "resolution": ["384x576"] },
    { "ratio": "1:1", "category": "inpaint", "resolution": ["512x512"] },
    { "ratio": "4:3", "category": "inpaint", "resolution": ["576x384"] },
    { "ratio": "3:4", "category": "inpaint", "resolution": ["384x576"] },
    { "ratio": "1:1", "category": "upscale", "resolution": ["1024x1024", "2048x2048"] }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `name` | **实现自己起的名**，客户端只显示、不解析。一个文件能命名它就用那个文件名；`render` 那种三件套没有单个文件可指，用实现自己给这一族起的名字。 |
| `files` | **实现挂载点**：每个模型角色一个条目。这就是“对内可替换”的接口 —— 客户端只看到“哪个角色、什么文件”。 |
| `ready` | 所有角色都就绪。`false` 时提交会得到 `no_model`。 |
| `missing` | 缺哪个角色，点名。 |
| `frames` | 这条能力**能出的画幅**（见 §4.3）。 |

**一条能力覆盖哪些场景是派生的，不是声明的**：三个场景指向同一个 checkpoint 就是**一条**能力，运维给 `inpaint` 单配一个 checkpoint 就变成**两条**。这样文档永远不可能声称一个“任务其实不会用到”的模型。

### 4.3 画幅 `frames`：唯一出处

**画幅不是算出来的，是手写的表**：`ratio` → 该比例下的 `resolution` 字符串数组。`resolution` 写成 `"宽x高"`（就是 `"512x512"` 这种字面量），**请求体里也发这个字符串**，客户端把菜单里挑中的那个原样发回来，全协议零格式化。

五条硬规矩：

1. **`abilities` 有序、`frames` 有序，顺序是规范的一部分。** 某个 `category` 的默认画幅 = 跨 `abilities` 按序扫、命中它的第一个 `frame` 的第一项；全局默认 = `abilities[0].frames[0]`。所以**表里的顺序就是客户端菜单的顺序**，也是省略 `resolution` 时的取值。
2. **`resolution` 可省略 ⇒ 取该 `category` 的第一档。** 这是**每个场景自己的默认**，不是全局共用一个。（规则表对实现的硬要求：每个场景至少有一档。）
3. **校验是成员检查。** `resolution` 不在该 `category` 的帧表里 ⇒ `400 unsupported_size`。**表就是全部合法值**，没有第二条路 —— 客户端**只选不算**，所以服务端也不接受它算出来的东西。
4. **本规范不约定支持哪些比例与分辨率。** 只要求两条，而且都是**装配期断言**（发布不出一份坏文档），不是运行期分支：
   - 每个 `category` 至少命中一档 `frame`；
   - `(category, resolution)` **唯一** —— 客户端只发这两个，服务端靠它反查模型，重复就是文档作者的错。
5. **`ratio` 是标签，不由数字反推。** `768 × 1344` 的精确比是 4:7，叫它 `9:16` 是**作者定的类目名**（和相机的画幅档位一个道理）。客户端**只显示、不计算**。

前端由此得到两步选择：**先选 `frame.ratio`，再选 `frame.resolution`**，零算术。

### 4.4 两个扩展通道

**层不同，所以通道不同**：前缀是层名，后缀是通道。读一眼就知道该往哪放。

| | `ext_params` | `chp_params` |
|---|---|---|
| 层 | **模型层**（这次画什么） | **CHP 层**（这次怎么连、怎么算账） |
| 住户 | **规范一个都不定义** | CHP 定义：目前只有 `password` |
| 谁校验 | 没有人。**原样携带、原样回显** | 参考实现校验 `password`（对不上就是 `401`） |
| 谁能加 | 任何人加任何字段，自己的客户端自己读 | 只有改协议能加 |

- **`ext_params` 没有官方字段表。** 放进去的字段完全由客户端自己定制，服务端**不筛不校验**，`job.ext_params` 原样带回（含嵌套结构）。这是“给自己的客户端加参数”的正式通道。
- 实现**可以读**其中自己认识的键（那是实现的行为，不是协议条文，所以写进它自己的 README，不写进本文）。参考实现认识两个：`step` 与 `negative_prompt`。
- **`chp_params` 只装“调用方必须随请求交上来的 CHP 层参数”**，今天只有 `password`。它不是“远程改设置”的通道 —— 部署调优（模型路径、采样参数、翻译后端）是运维在那台机器上改的，**根本不出现在 HTTP 上**。
- **`ext_params` / `chp_params` 里的未知键不给任何错误码**：忽略 + 回显，不是错误。
- **顶层闸门是硬的**：不在 §4.5 那张表里的顶层字段**直接忽略，不报错**，名字回显到 `job.ignored`。

### 4.5 字段表

| 字段 | 类型 | 必填 | 语义（冻结） | 越界处理 |
|---|---|---|---|---|
| `category` | string | 是 | 场景名，§3 里 `rules[].category` 的一个 | 不认 → `400 unsupported_category` |
| `resolution` | string | 否 | `"宽x高"`，**必须逐项命中该 `category` 的帧表**；省略取第一档 | `400 unsupported_size` |
| `prompt` | string | 否 | 画面描述。是否先译英由 `prompt.language` 决定（§5） | — |
| `seed` | int | 否 | **必要参数**：`0` = 每次不同，同一个值可复现。**留在顶层而不是扩展通道，是因为少了它前端就无法锁定重复生成。** | 负数 → `400 bad_request` |
| `ref_strength` | number | 否 | **0.05–0.95，越大越贴近参考图** | 夹到边界并在 `job` 回显 |
| `image_base64` | string | 看 `needs.image` | 参考图，base64 PNG/JPEG，允许带 `data:` 前缀 | `400 bad_image` |
| `mask_base64` | string | 看 `needs.mask` | 蒙版，**黑底白区，白 = 要重画** | `400 bad_mask` |
| `ext_params` | object | 否 | 模型层扩展参数，**原样携带、原样回显**，规范不定义任何字段 | — |
| `chp_params` | object | 否 | CHP 层扩展参数，目前只有 `password` | 密码不对 → `401` |

两条统一规则，全规范只写一次：

1. **枚举按枚举判，连续量按边界判**：`resolution` 不在帧表里 → `unsupported_size`（成员检查，不是数值域）；`ref_strength` 越界 → **夹到边界并回显**，不报错。
2. **未认字段一律忽略 + 回显**，不报错。

> **上表只覆盖 `endpoints.jobs` 的提交体。** 语音那条路不套作业模型，请求体是 `text` / `voice` / `stream` 这几个字段，见 §4.8 —— 两边**不共用**这张表，别把 `text` 当成 `prompt` 发过来。

**其余顶层字段一律忽略，名字进 `job.ignored`。** `chp/1` 的 `capability` / `task` / `size` / `steps` / `negative_prompt` 都**不再被识别**为这两个通道之外的字段，所以它们会像任何陌生字段一样被点名 —— 这正是让一次改名看得见、而不是静默失效的机制。

### 4.6 `ref_strength` 为什么要这样定

它只声明**方向**（越大越贴近参考图）和**值域**（0.05–0.95）。至于实现怎么做到：

- 在 img2img 家族里可能是“降低去噪强度”；
- 在参考条件生成家族里可能是“把参考图柔化”（它没有可保留的初始 latent，靠模糊表达“别抄得那么紧”）；

两种机制都满足“越大越贴近”，因此**都合规**。客户端的滑杆、文案、默认值处理逻辑完全一样。

### 4.7 鉴权：一个请求只用一种载体

| 请求 | 载体 |
|---|---|
| **带 body 的 `POST`**（提交任务、翻译、语音） | `chp_params.password` |
| `GET` 与**无 body 的 `POST`**（轮询、取状态、取图、取消） | `Authorization: Bearer <password>` —— **唯一例外，理由是密码不进 URL 也不进日志** |

参考实现**也可以**接受别的头部写法，但那条规矩是“新写的按字段、拿不到 body 时才用头”，不是把老路堵死。

密码为空 = **不校验**，信息文档的 `auth.required` 会如实说是 `false`。密码不对 → `401 unauthorized`，**作业不入队**。空密码这条**在本版没有被取消**（见 §1.1.1 的两态表）：用户的工作流与卡片里存的可能就是空密码。

#### 4.7.1 授权粒度 = `category`，分「播报」与「执行」两层

**授权粒度是 `category`**（对外的一个接口/场景），**不按模型文件** —— 模型文件名只对那台机器成立，而 key 是设备级的，粒度太细没有意义。

| 层 | 做什么 | 漏了会怎样 |
|---|---|---|
| **播报**（§1.1.1） | 文档里只列这把 key 授权到的条目 | 界面上多出一个点不动的选项 |
| **执行**（承重） | `endpoints.jobs` 与 `endpoints.speech` **每次**校验请求的 `category` 是否在该 key 的授权集里，不在 ⇒ **`403 forbidden_capability`** | **权限形同不存在**：知道名字的人直接 POST 就绕过了界面 |

**「对外可用」不需要第三个开关。** 因为信息接口现在需要 key，**没有 key 就等于什么都没有对外**；「对外可用的模型」完全由「有没有一把 key 授权它」决定，不设全局开关，少一层就少一处「为什么它不出现」的歧义。

**默认 key**：实现里那个既有的「密码」配置（以及它的环境变量）**继续有效**，语义升级为**默认 key**，权限等价于全部 `category`。⇒ 老用户的工作流与卡片**零改动**继续能用。它只在管理面里**只读显示**（来源不是 key 表）。

### 4.8 顶层键 `speech`（语音 / TTS）

```json
"speech": {
  "rules": [
    { "category": "speak", "rule": "txt-2-sph", "needs": { "text": true } }
  ],
  "abilities": [
    { "name": "qwen3-tts-0.6b", "ready": true, "missing": [],
      "files": { "engine": "qwen3-tts-12hz-0.6b-customvoice-q8_0.gguf" },
      "audio": { "sample_rate": 24000, "channels": 1, "formats": ["pcm", "wav"], "streaming": true },
      "voices": [ { "id": "vivian", "label": "Vivian", "languages": ["zh", "en"] } ] }
  ]
}
```

**五处定稿**（每条都是把图片侧既有想法平移到语音）：

1. **两张表照旧**：`rules` 是「客户端要什么」，`abilities` 是「谁能答」。
2. **音色菜单是手写的 `voices`，顺序即规范**（同 `frames`）：第一个即默认音色；客户端**只选不算**、服务端**成员校验**，未知音色回 `unsupported_voice`。有些引擎的 `/v1/voices` 是空的 ⇒ 这张表**只能**由实现手写并播报。
3. **模态加一个字**：`sph`（speech）。`txt-2-sph` 落进既有的 `<模态> -2- <输出>` 文法，**不新增轴**。
4. **`audio` 是这份能力自己的输出规格**，客户端**读它、不猜它**。
5. **`files.engine` 用引擎自己的模型文件名**，与图片侧 `files.checkpoint` 同一个位置、同一个道理。

**语音那份请求 schema 装在 `speech.input_schemas` 里**，键就是规则条目的 `input`（`txt-2-sph/v1`）—— 与图片侧同一条规矩（§4.1「同一规则共用一份 schema」、§4.3「`input` 指向 `input_schemas` 的键」），只是这一份与 `speech` 自己的两张表放在一起。**顶层那个 `input_schemas` 仍然只有图片侧那三份**：加语音段不许碰旧表 —— 图片侧那三张表（`rules` / `abilities` / `input_schemas`）的**字节与升级前相同**。

**字段名是 `text` 而不是 `prompt`（承重）**：`prompt` 在 CHP 里带副作用 —— `rules[].prompt.language` 为 `"en"` 会让服务端在提交路径上**自动翻译**，把中文念成英文。**`speech` 的文本永不翻译**，这一句是规则，不是建议。`text` 还与模态名 `txt` 同字，符合既有构词法。

**传输：一条路由，`stream` 决定内容类型，不套作业模型。**

| | 图片 | 语音 |
|---|---|---|
| 形态 | 提交作业 → 轮询 → 取件 | **一次请求，边合成边回字节** |
| 路由 | `jobs` / `job` / `progress` / `output` / `cancel` | `speech` 一个 |

`stream: true` ⇒ `Content-Type: audio/pcm`，按 `abilities[].audio.sample_rate` 的裸 PCM 流式回写；`stream: false` ⇒ 一次返回 `audio/wav`。同一个端点、两种内容类型，是引擎已有的行为。**错误一律是 JSON，且在开始写 body 之前就用状态码定好** —— 客户端的判据是「先看状态码，非 2xx 就按 JSON 解析」。

**「正在唤醒」不新增错误码**：它复用既有的 `busy`（可重试语义）。后端缺席不等于服务缺席，但也不该让客户端区分两个它其实不需要区分的状态。

**后端地址与令牌永不进文档、永不进响应** —— 无论后端是连不上、令牌错还是 500，都收敛成 §6 里那几条码，明细**只进那台机器的日志**（`translate.py` 已在遵守的同一条规矩）。

### 4.9 管理面：存在，但不是协议的一部分

实现**可以**带一个 web 控制台来管 key 与 key 的授权集。三条定稿：

1. **不进 `endpoints`。** 客户端只从 `endpoints` 读地址 ⇒ 它**永远不知道控制台存在**，契约保持干净。
2. **凭据是独立的一条线**，与数据面的 key **完全分开**。⚠ 因为数据面的取值也认 `Basic`（取 `:` 之后那段当 key），控制台**必须是独立的路由族**，不经过数据面的取值逻辑；并且 **key 表里不许登记与控制台凭据同值的 key**，否则控制台密码会顺带变成数据面钥匙。
3. **能力边界：只能管 key 与 key 的授权集。** 不能新增能力、不能改模型配置、不能改凭据。**控制台里不存在「添加一个模型」这个动作** —— 那个清单**就是**实现代码里注册的 `category` 表，页面上的勾选项只能出自它；清单外的 `category` 一律拒收。

| 层 | 谁定 | 生效方式 |
|---|---|---|
| **能力的存在与形状**（有哪些对外接口、走什么图、什么 signature） | **开发者改代码** | 改完重启 |
| **能力的开关与授权**（哪把 key 能用哪些接口） | **管理员点控制台** | 热生效 |

「图构造是逻辑，不该数据化」：让控制台能新增能力，会退化成在图数据库里手工拼 JSON，之后没人能查。

## 5. 翻译：推荐流程

**这是推荐流程，不是规则。** 客户端可以自己先翻译、可以把译文展示给用户；后端在提交时兜底，只是为了“客户端什么都不做也不会做错”。

### 5.1 触发条件（两个都满足才翻）

1. 该场景的 `prompt.language == "en"`；
2. `prompt` **含非 ASCII 可打印字符**。

第 2 条刻意不是“含中日韩文”。俄语、希腊语、阿拉伯语、泰语同样会让只认英文的文本编码器变成噪声 —— 判据必须是“**是不是全 ASCII**”，而不是“有没有中文”。

### 5.2 流程

```
提交 → 需要翻? ─否→ 用原文建图
              └是→ 查翻译记忆库 ─命中→ 用译文
                              └未命中→ 调翻译后端 → 成功则存库并用译文
                                                    └失败→ 用原文建图(任务不失败)
```

无论走哪条路，响应里的 `prompt` / `prompt_source` / `translated` 三个字段都会如实告诉你发生了什么。

### 5.3 翻译记忆库

- 落盘在实现自己的目录里，重装插件、重启进程都不丢。
- **键 = 原文 + 目标语言。** 一条翻译是**语言事实**：“一只猫在沙发上 → a cat on a sofa”对不对，与哪个引擎翻的无关，也与源语言是什么无关（原文自己就确定了它）。所以引擎、模型、提示词版本**都不进键**。
- 引擎与时间作为**旁注**存在条目里 —— 不进键，但留着。将来想用更好的引擎把整库重刷一遍时，靠它筛。
- 失败不入库。上限可配，超出按最旧淘汰。
- 记忆库存在**后端**而不是客户端，意义在于：任何客户端（包括只会发 curl 的第三方工具）都自动共享同一份成果。

### 5.4 提前翻译

`endpoints.translate` 给“想提前预热”或“想给用户看译文”的客户端用，不是必需步骤。

请求 `{ "texts": ["…"], "target": "en" }` →
`{ "engine": "…", "target": "en", "available": true,
   "results": [ { "source": "…", "text": "…", "translated": true, "cached": true } ] }`

- 纯 ASCII 的文本原样返回，`translated: false`。
- 任何失败都返回原文，绝不丢用户写的内容。

### 5.5 后端

翻译后端只要求一条：提供 **OpenAI 兼容的 `POST {url}/v1/chat/completions`**。这一条覆盖 llama.cpp、vLLM、Ollama、各家云 API。**后端地址没有默认值** —— 默认是空的，也就是关闭。规范不允许厂商把某一个部署的地址写进默认值。

## 6. 错误

```json
{ "error": "no_model", "message": "…", "detail": { … } }
```

| `error` | HTTP | 含义 |
|---|---|---|
| `unauthorized` | 401 | 密码/key 不对，未入队。**只有它的响应体多一个 `spec`**（§1.1.1） |
| `bad_request` | 400 | 请求体不是合法 JSON / 字段类型不对 |
| `unsupported_category` | 400 | 不认识这个 `category` |
| `unsupported_size` | 400 | `resolution` 不在该场景的帧表里 |
| `unsupported_steps` | 400 | **参考实现自己的键** `ext_params.step` 越出了它的枚举；裸规范里没有这条，因为规范不定义 `ext_params` 的任何字段 |
| `bad_image` | 400 | 参考图不是合法 base64 PNG/JPEG |
| `bad_mask` | 400 | 需要蒙版但没给 / 不合法 |
| `stretched_reference` | 400 | 参考图的宽高比与本次画幅不一致，按画幅缩放会把它压变形；这是**实现**的防空转闸门，保留在此以便客户端识别 |
| `forbidden_capability` | 403 | **这把 key 没有这个能力**（执行层的拒收，§4.7.1） |
| `unsupported_voice` | 400 | 这台引擎没有这个音色，请从文档的 `speech.abilities[].voices` 里取（§4.8） |
| `no_model` | 409 | 场景要用的模型角色没配齐 |
| `no_engine` | 409 | 没有可用的语音引擎（未配地址 / 连不上 / 引擎回 401），见 §4.8 |
| `invalid_workflow` | 400 | 生成图校验失败（多为节点或模型缺失） |
| `busy` | 429 | 队列已满；**也用于「后端正在唤醒」**，语义是「稍后再试」 |
| `not_found` | 404 | 作业不存在 / 已过期 |
| `speech_failed` | 502 | 语音引擎没有正常应答（回 500 或其他） |
| `internal` | 500 | 后端内部错误 |

`message` 是给人看的，客户端可以直接显示；`detail` 是给程序看的，结构随 `error` 而变。参考实现把自己认得的这串错误码也放进信息文档的 `errors`，客户端**不必自己抄一遍**。

**后端侧的任何失败都不许把后端地址或令牌漏给客户端**（§4.8）：连不上、令牌错、后端 500 一律收敛成 `no_engine` / `speech_failed`，明细只进那台机器的日志。

## 7. 与其他规范的取舍

**借了 MCP 的三样思想**：

- `abilities[]` 的形状对应 MCP 的 tool descriptor（哪些文件能跑、能出什么）；
- `input_schemas` 用完整 JSON Schema，而不是“表单够用的子集”；
- `spec` 字段对应 MCP `initialize` 的协议版本协商 —— 都靠“版本在消息里”而不是“版本在路径里”。

**没有采用 MCP 的传输层**，原因有三：MCP 没有标准化的图片上传通道（而本规范的请求体要内联最多几十 MB 的 base64 图）；MCP 客户端是有状态机（会话 ID、SSE），而这里的客户端很多只是一个 WebView 里的几十行 HTTP 调用；作业模型是“提交 → 轮询 → 取图”，而轮询对“切后台 / 断网重连”比长连接更稳。

**将来若需要**让 LLM 代理直接调用，可以再挂一个门面，由**同一份**场景定义生成 —— 那是第二个投影，不是重写。

## 8. 明确不做（收敛清单）

以下都是**有意不做**，不是遗漏：

- 不做 OpenAPI 文档生成。
- 不做 MCP / JSON-RPC 门面（留作将来的第二个投影）。
- 不做推送、SSE、Webhook（轮询够用且更稳）。
- **不做“用户自带工作流”入口。** 推荐路径就是用户直接改 CHP 插件，而不是让协议背一套工作流上传/校验/沙箱。
- 不做多目标语言的翻译（`target` 只有 `en`；记忆库的键留了位置）。
- 不做**别名机制**、不写兼容层、不认 `chp/1` 的字段拼写：`chp/2` 不承诺读得动上一版（§0 第 3 条）。
- 不做**场景级独立版本号**（`rule` + `input` 已经足够）。
- 不做插件化的家族注册机制（参考实现里两个家族，两个普通模块就够）。
- 不做账号、配额、计费；**权限分级只到「key × `category`」这一档**（§4.7.1），不做角色、分组、继承、有效期 —— 再往上加就是在协议里写一个没人会去维护的 RBAC。
- 不做 `deprecated` 之类的字段 —— **不定义用不到的东西**。
- **不规定端口，也不规定信息接口的路径**（§1.3）：只要求“网络可达”（能不能连上；鉴权是另一件事，见 §1.1.1）与“地址从文档里读”。
- **不约定支持哪些比例与分辨率**（§4.3）：只要求“每场景至少一档”。
